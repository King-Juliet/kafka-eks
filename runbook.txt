PHASE 1 - CLUSTER AND CONTROLLERS  (terraform/<region>)
--------------------------------------------------------------------------------
5.  Apply in three moves: base -> tunnel -> the rest
    (Why: the Kubernetes API accepts only the bastion's Elastic IP, so from your Mac Terraform and kubectl
     reach it through a Session Manager tunnel via the bastion. The tunnel can only be opened once the
     cluster and the bastion exist. Details: README, "Reaching the Kubernetes API".)
    cd $TF_DIR
    terraform init

    5a. Base: VPC, KMS keys, bastion, EKS control plane and system nodes
        terraform apply -target=module.eks
        (-target also builds what module.eks needs. Terraform warns that targeting is in use: expected, once.
         Do not leave the base without the rest: only step 5d builds everything else.)

    5b. Wait until the bastion is registered in Systems Manager (usually a minute or two after it starts)
        export CLUSTER=kafka-test                           # = the default of var.cluster_name
        BASTION_ID=$(aws ec2 describe-instances --region $AWS_REGION \
          --filters "Name=tag:Name,Values=$CLUSTER-bastion" "Name=instance-state-name,Values=running" \
          --query 'Reservations[0].Instances[0].InstanceId' --output text)
        aws ssm describe-instance-information --region $AWS_REGION \
          --filters Key=InstanceIds,Values=$BASTION_ID \
          --query 'InstanceInformationList[0].PingStatus' --output text      # must print Online
        (Prints None or nothing: wait a minute and repeat. Still nothing after several minutes: the bastion
         cannot reach Systems Manager; check it has the Elastic IP and the public route table has the
         internet-gateway route.)

    5c. Open the tunnel in a SECOND terminal and leave it running
        (Set AWS_REGION, CLUSTER and BASTION_ID there too, same values as above.)
        API_HOST=$(aws eks describe-cluster --region $AWS_REGION --name $CLUSTER \
          --query cluster.endpoint --output text | sed 's#https://##')
        API_IP=$(dig +short A $API_HOST | grep -E '^[0-9.]+$' | head -n 1)       # must print an IP
        aws ssm start-session --region $AWS_REGION --target $BASTION_ID \
          --document-name AWS-StartPortForwardingSessionToRemoteHost \
          --parameters host=$API_IP,portNumber=443,localPortNumber=8443          # 8443 = var.api_tunnel_port
        (It prints "Waiting for connections..." and stays in the foreground. That terminal IS the tunnel:
         closing it cuts Terraform and kubectl off from the cluster. After step 5d, the same command is
         available as:  eval "$(terraform output -raw api_tunnel_command)"  )
        (The bastion connects to $API_IP across the internet, from its Elastic IP, which is exactly what the
         cluster allows. $API_IP is looked up from your Mac so the bastion does not resolve the name to the
         VPC-internal address.)

    5d. Back in the first terminal: everything else
        terraform plan -out=tfplan
        terraform apply tfplan                              # the slow part: add-ons and the Helm releases
        (Roughly 25-30 min for all of step 5 together: an estimate, not measured.)
        (Every other value has a default in $TF_DIR/variables.tf; to change one, edit its default there.)
        (Any later plan / apply / destroy needs the tunnel open. "connection refused" on localhost:8443,
         or a timeout, means the tunnel stopped: rerun the 5c command and rerun Terraform; it carries on
         where it stopped. I could not test how the tunnel copes with Terraform's many parallel
         connections; if you see resets, add -parallelism=2 to plan / apply.)
